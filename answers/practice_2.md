## 1. Почему нельзя постоянно коммитить в main?

Прямые изменения обходят независимую проверку и могут нарушить работоспособность общей ветки. В принятом GitHub Flow изменения проходят feature-ветку, PR, review и проверки. Учебные прямые коммиты в main выполнены только там, где это прямо требует упражнение.

## 2. Шаги GitHub Flow

Создать ветку от актуальной main, сделать небольшие коммиты, отправить ветку, открыть PR, получить отзыв, исправить замечания, пройти проверки, выполнить merge и удалить завершённую feature-ветку.

## 3. Чем PR отличается от merge?

Merge - операция объединения истории Git. Pull Request - запрос на обсуждение и проверку изменений на площадке, который может включать diff, комментарии, проверки CI и последующее слияние.

## 4. Что такое Code Review?

Проверка изменений другим участником перед интеграцией. Она помогает обнаружить ошибки, уточнить требования и распространить знание о коде. Самопроверка автора не заменяет требуемое парное ревью.

## 5. Git и SVN

Git хранит локально историю и позволяет делать коммиты и ветки без сервера. SVN опирается на центральный репозиторий; для фиксации новой ревизии нужен доступ к нему. Доступность интернета и доступность сервера - разные условия.

## 6. Что означает feat:?

Тип feat в Conventional Commits обозначает новую функциональность. Общий вид: type(scope): description; scope необязателен.

## 7. Как впервые отправить ветку?

git push -u origin feature/hobby-project. Флаг -u задаёт upstream-связь для дальнейших git push и git pull.

## 8. Зачем DevOps-инженеру терминал?

На удалённом сервере графической IDE может не быть. CLI позволяет воспроизводить операции, диагностировать состояние и автоматизировать Git в скриптах и CI.
