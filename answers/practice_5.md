# Письменные ответы по работе 5

## 1. Чем обусловлена невозможность входящего соединения с гостевой системой при использовании адаптера типа NAT и возможность такового при использовании адаптера типа Host-only?

NAT транслятор допускает ответы на исходящие соединения, но входящему пакету без правила проброса не соответствует гостевой адрес. Host-only создаёт непосредственно связанный с хостом сегмент, поэтому хост обращается к гостю по его IP.

## 2. Каково назначение файлов ~/.ssh/known_hosts и ~/.ssh/authorized_keys? На какой из систем размещается каждый из них?

known_hosts находится у SSH-клиента и хранит доверенные ключи серверов; authorized_keys находится в домашнем каталоге пользователя сервера и перечисляет ключи допущенных клиентов. Это две независимые стороны аутентификации.

## 3. Обоснуйте преимущество аутентификации по ключу перед парольной с учётом того, что оба типа учётных данных передаются по защищённому каналу.

Клиент доказывает владение закрытым ключом подписью, не передавая сам секрет серверу. Открытый ключ нельзя использовать для входа. Длинный случайный ключ практически непригоден для перебора; пароль часто короток, повторно используется и может быть выманен. Закрытый ключ всё равно нужно защищать правами и при необходимости парольной фразой.

## 4. В чём состоит различие действий ufw allow и ufw limit?

allow разрешает подходящие соединения, limit дополнительно ограничивает частоту новых соединений с одного адреса. Длительная уже установленная SSH-сессия не требует нового подключения для каждой команды.

## 5. Администратор внёс изменения в файл sshd_config удалённого сервера, перезапустил службу и завершил сессию. Последующие попытки подключения завершаются сообщением Connection refused. Определите нарушение процедуры, а не конфигурации. Укажите две команды, применение которых исключило бы такой исход.

Нарушены проверка до применения и сохранение действующего доступа. Перед перезапуском нужны sudo sshd -t и проверка нового подключения командой ssh devops из второй сессии. После применения sudo ss -tlnp подтверждает фактический сокет. Старую сессию закрывают только после успешной проверки новой.

## 6. На удалённом сервере по SSH выполнена последовательность команд ufw default deny incoming, ufw enable, ufw allow 22/tcp. Определите результат и команду, на которой он наступает. Приведите корректный порядок.

При включении ufw с deny incoming и без разрешающего правила новые управляющие подключения блокируются; действующая сессия может сохраниться благодаря conntrack, поэтому немедленный обрыв не гарантирован. На критическом шаге ufw enable доступ оказывается под угрозой. Правильный порядок: default deny incoming, allow 2222/tcp, затем enable и проверка нового подключения.

## 7. Порт службы SSH изменён на 2222, выполнена команда sudo ufw allow ssh. Правило присутствует в выводе команды ufw status, однако соединение не устанавливается. Укажите источник, из которого утилита определяет номер порта по символьному имени.

Символьное имя ssh разрешается через /etc/services в TCP 22. UFW не читает Port из sshd_config. Нужно явно разрешить фактический 2222/tcp.

## 8. Дайте оценку тезису: «Изменение порта службы SSH представляет собой security through obscurity, поскольку фактический порт определяется сканированием за незначительное время, и защищённость не повышается». Укажите, какая задача данной мерой действительно решается и какая не решается.

Перенос порта уменьшает шум автоматического сканирования стандартного 22 и нагрузку от массового перебора. Он не скрывает службу от целевого сканирования и не заменяет ключи, запрет root и обновления.

## 9. При подключении получено предупреждение REMOTE HOST IDENTIFICATION HAS CHANGED. Назовите три возможные причины и опишите действия по разграничению штатной причины и признака атаки. Обоснуйте, почему безусловное применение команды ssh-keygen -R является некорректной практикой.

Причины: пересоздан сервер или ключи, адрес теперь принадлежит другому узлу, либо происходит подмена сервера. Нужно сверить отпечаток через независимую консоль и проверить историю изменений и адрес. ssh-keygen -R допустим только после подтверждения штатной замены; без проверки он удаляет защитное свидетельство.

## 10. Закрытый ключ перенесён на другую рабочую станцию, клиент отказывается его использовать, указывая на незащищённость файла. Обоснуйте, по какой причине клиент контролирует права доступа к файлу, принадлежащему самому пользователю, и от какого класса угроз это защищает.

Другой локальный пользователь или процесс с его правами мог прочитать файл с широкими правами и затем войти от имени владельца. Владелец файла не означает исключительного доступа к его содержимому. chmod 600 ограничивает чтение и запись владельцем, каталог .ssh обычно 700.

## 11. На сервере команда ping myapp.local выполняется успешно, команда dig myapp.local возвращает пустой ответ. Объясните отсутствие противоречия и приведите полный порядок разрешения имён.

ping использует системный механизм разрешения имён (NSS), а dig обращается к DNS напрямую и не читает /etc/hosts. В Ubuntu порядок задаётся hosts: в /etc/nsswitch.conf: обычно files, затем локальный резолвер/DNS; systemd-resolved использует кэш и вышестоящие серверы. Для .local возможен отдельный mDNS в зависимости от NSS.

## 12. В команде ssh -L 9090:127.0.0.1:8080 user@server укажите, в адресном пространстве какой системы интерпретируется адрес 127.0.0.1. Обоснуйте, почему межсетевой экран сервера не препятствует такому соединению при закрытом порте 8080.

127.0.0.1 после второго двоеточия относится к серверу. Клиентский порт 9090 передаёт данные внутри SSH через разрешённый 2222, после чего sshd открывает локальное соединение к серверному 8080. Внешний входящий трафик на 8080 не возникает.

## 13. Механизм sudo регистрирует исполнителя и текст команды. Оцените достаточность этой меры для расследования инцидента при наличии у администраторов возможности выполнить sudo su -. Предложите способ устранения выявленного недостатка.

Журнал sudo su - фиксирует запуск корневой оболочки, но не гарантирует аудит всех её последующих команд; root способен менять локальные журналы. Нужны ограниченные команды sudo вместо полной оболочки, запись ввода/вывода сессии и пересылка журналов на отдельный защищённый узел.

## 14. Конфигурирование сервера в настоящей работе выполнялось вручную, тогда как в практической работе № 11 аналогичный результат достигается средствами Ansible. Назовите три недостатка ручного конфигурирования, не проявляющихся при управлении единичным узлом.

На многих узлах ручная настройка вызывает расхождения конфигураций, плохо воспроизводится и плохо проверяется после изменений. Ansible описывает желаемое состояние в версии, повторяет его на узлах и предоставляет контролируемое идемпотентное применение.
