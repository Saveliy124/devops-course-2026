# Письменные ответы по работе 6

## 1. Из каких элементов состоят HTTP-запрос и HTTP-ответ? Как Nginx выбирает блок server и какой блок обработает запрос, заголовок Host которого не совпадает ни с одной директивой server_name?

Запрос содержит метод, путь и версию, заголовки и возможное тело; ответ — версию и статус, заголовки и тело. Nginx сначала учитывает адрес/порт, затем имя server_name и Host, а при TLS также SNI для выбора сертификата. Неизвестное имя попадёт в default_server данного сокета, а без него в первый server.

## 2. Чем различаются коды 301 и 302? Обоснуйте выбор кода для перенаправления с HTTP на HTTPS.

301 означает постоянный перенос, 302 временный. Переход на HTTPS принят постоянным, поэтому 301 сообщает клиенту постоянный новый адрес; в работе требуется именно он. Клиент может кэшировать 301.

## 3. Администратор изменил конфигурацию и выполнил systemctl restart nginx, после чего сервер перестал обслуживать все ресурсы. Определите нарушение процедуры и объясните, чем в этой ситуации reload отличается от restart.

Администратор пропустил nginx -t и использовал restart без необходимости. restart останавливает текущую службу и затем пытается запустить новую; при ошибке она недоступна. reload при успешной проверке плавно меняет рабочие процессы, а ошибочная конфигурация не заменяет действующую.

## 4. Зачем конфигурации разделены на sites-available и sites-enabled? Как отключить ресурс, сохранив его конфигурацию?

sites-available хранит определения, sites-enabled выбирает активные через ссылки. Удаление ссылки и nginx -t && systemctl reload nginx отключает ресурс, сохраняя его конфигурацию.

## 5. Почему главный процесс работает от имени root, а рабочие — от имени www-data? Как Nginx использует ключ с правами 600 и владельцем root?

Главный процесс root открывает привилегированные порты и читает ключ при запуске или reload. Он создаёт рабочие процессы с нужным TLS-контекстом; www-data обслуживает запросы без права чтения закрытого ключа с диска.

## 6. Какие задачи TLS решаются при использовании самоподписанного сертификата, а какая нет? Как в задании 2 обеспечено доверие к сертификату без обращения к удостоверяющему центру? Почему сертификат без поля SAN отклоняется браузером даже при совпадении CN с именем ресурса?

Самоподписанный сертификат позволяет шифрование и проверку целостности, но автоматически не подтверждает личность владельца. Доверие установлено копированием публичного сертификата по проверенному SSH и явным --cacert. SAN содержит допустимые имена; современные браузеры проверяют именно SAN, одного CN недостаточно.

## 7. В конфигурацию добавлен заголовок HSTS со значением max-age=31536000, после чего сертификат сформирован повторно. Браузер отказывает в доступе без возможности продолжить. Объясните причину и укажите, на какой стороне устраняются последствия.

HSTS сохраняется на стороне клиента и запрещает обход ошибки TLS для этого имени. После замены самоподписанного сертификата старое доверие не подходит. Нужно корректно установить доверие новому сертификату или очистить соответствующее состояние HSTS в браузере; изменение конфигурации сервера не стирает уже сохранённую политику клиента.

## 8. Доступ к серверу возможен только через проброс портов NAT: порт хоста 8443 → порт гостя 443, порт 8080 → порт 80. Куда директива return 301 https://$host$request_uri направит браузер при обращении к http://localhost:8080? Какое свойство сегмента Host-only устраняет проблему?

$host обычно не содержит порт, поэтому Location будет https://localhost/ на стандартном 443, а не на 8443. Host-only позволяет напрямую использовать гостевые 80 и 443 по одному адресу и имени без несовпадения портов хоста и гостя.

## 9. Файл index.html имеет права 644, но ресурс возвращает 403 Forbidden. Назовите причину, не связанную с правами самого файла, и укажите, какой командой проверить права на всех компонентах пути. Почему каталог с правами 711 позволяет отдавать файлы, а с правами 744 — нет?

Не хватает x на одном из каталогов пути; проверить namei -l /var/www/devops-site/index.html. 711 разрешает проход по известному имени, но не просмотр списка. 744 даёт список без прохода, поэтому открыть известный файл всё равно нельзя.

## 10. Почему каталог ресурса принадлежит devops, а не root и не www-data? К каким последствиям привело бы право записи у www-data?

devops доставляет и изменяет ресурс, www-data только читает. root потребовал бы повышения привилегий при каждом деплое. Запись для www-data превращает выполнение кода в приложении в возможность подменить опубликованные файлы.

## 11. Выполнена команда rsync -avz --delete site devops:/var/www/devops-site/. Изменения на ресурсе не появились. Объясните, что сделала команда и какие файлы удалил бы флаг -- delete.

Без завершающего / копируется каталог site внутрь /var/www/devops-site/site. --delete действует в синхронизируемом поддереве назначения, а не произвольно по всему серверу; он удаляет там объекты, отсутствующие в соответствующем источнике. Корневая index.html при таком ошибочном вложении не обновляется.

## 12. Какую проблему решает параметр --chmod? Приведите два исхода доставки без него: нарушающий доступность ресурса и нарушающий его защищённость.

--chmod=D755,F644 задаёт предсказуемые права независимо от локальной файловой системы. Без него 600 на index.html приводит к 403; 666 разрешает www-data подменить содержимое. Права дополняют, а не заменяют правильного владельца.

## 13. Сценарий деплоя открывал три SSH-соединения за запуск. После нескольких запусков подряд соединения стали отклоняться. Определите причину и предложите два способа устранения, не ослабляющих защиту сервера.

Три SSH-соединения на запуск быстро достигают лимита UFW. Можно объединить операции в одну сессию/один rsync либо использовать SSH ControlMaster для повторного использования защищённого соединения. Ослаблять limit не требуется.

## 14. Каково назначение set -euo pipefail и curl -f? Почему сценарий, всегда завершающийся с кодом 0, непригоден для конвейера непрерывной интеграции?

set -e завершает сценарий при необработанной ошибке, -u обнаруживает необъявленные переменные, pipefail учитывает ошибки всех элементов конвейера. curl -f возвращает ошибку на HTTP 4xx/5xx. Постоянный код 0 скрывает отказ от CI, поэтому конвейер ошибочно продолжит работу.
