# Письменные ответы по работе 7

## 1. Какие механизмы ядра Linux обеспечивают изоляцию контейнера? Почему контейнер запускается быстрее виртуальной машины?

Namespaces изолируют видимость процессов, сети и монтирований; cgroups ограничивают ресурсы; права, capabilities и seccomp сужают возможности. Контейнер запускает процесс на общем ядре, без отдельной загрузки ОС, поэтому стартует быстрее VM.

## 2. Изменение app.py привело к пересборке за секунды, изменение requirements.txt — к повторной установке всех зависимостей. Объясните по механизму кэширования слоёв. Что изменится, если обе инструкции COPY заменить одной COPY . . перед RUN pip install?

COPY requirements.txt и pip install предшествуют COPY app.py, поэтому изменение кода повторяет только последние слои. Изменение зависимостей инвалидирует слой pip и всё ниже. COPY . . перед pip привязывает кэш зависимостей к любому изменённому файлу контекста.

## 3. Приложение, запущенное командой docker run, получает отказ в соединении с СУБД по адресу localhost. Объясните причину. Каким образом приложение находит СУБД в конфигурации Compose?

localhost внутри контейнера означает сам контейнер приложения, а не VM и не соседнюю СУБД. В Compose DB_HOST=db, пользовательская сеть и встроенный DNS сопоставляют имя сервиса адресу контейнера db.

## 4. Чем depends_on с условием service_healthy отличается от depends_on без условия? Какую ошибку предотвращает это условие?

Без условия Compose упорядочивает запуск процессов, но не ждёт готовности БД. service_healthy ожидает успешный pg_isready и предотвращает раннее обращение к ещё инициализирующейся СУБД. Приложению всё равно полезны повторы при последующих сбоях.

## 5. Что происходит с данными СУБД после docker compose down и после docker compose down -v? Почему для сервиса с томом тег postgres:16-alpine предпочтительнее postgres:latest?

down удаляет контейнеры и сеть, но оставляет именованный том. down -v удаляет также том с базой. 16-alpine закрепляет основную версию, тогда как latest может сменить её и оказаться несовместимым с форматом сохранённых данных.

## 6. Порт 5001 не разрешён правилами UFW, но доступен с хостовой системы (шаг 3.1). Объясните механизм и назовите способ, исключающий такой доступ.

Docker добавляет правила DNAT/FORWARD; опубликованный порт может обходить обычные правила UFW для INPUT. Привязка публикации к 127.0.0.1 в актуальном Engine исключает прямой вход из сети, Nginx обращается к нему локально.

## 7. Учётной записи без права sudo добавлена группа docker. Покажите, каким образом она может получить права root на сервере, и сопоставьте с моделью разграничения привилегий из практической работы № 5.

Участник docker может запустить контейнер с --user root и -v /:/host, изменив /host/etc/sudoers или другие файлы хоста. Это эквивалент административного доступа, поэтому группу следует выдавать только доверенному администратору, как sudo.

## 8. Обращение к https://devops.local/app/ возвращает 502 Bad Gateway. Назовите две возможные причины и порядок диагностики.

502 возможен при остановленном приложении или неверном адресе/порте upstream. Сначала curl к Nginx и журнал devops-site.error.log, затем ss и curl к 127.0.0.1:5000, docker compose ps и logs. Если приложение отвечает 500, отдельно проверяют журнал приложения, состояние БД и DB_HOST; это другой участок отказа.
