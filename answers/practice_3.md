## 1. Merge и rebase: когда применять?

Merge соединяет линии истории и при настоящем слиянии создаёт коммит с несколькими родителями. Rebase повторно применяет коммиты на другой базе, меняя их хеши. Merge удобен для общих веток; rebase - для подготовки собственных неопубликованных изменений.

## 2. Почему опасен rebase общей ветки?

У коллег останется старая история, а на сервере после force-push появится новая. Возникают расхождения и риск повторного применения изменений. Переписывать общую историю можно только после явного согласования.

## 3. Что делает git rebase -i HEAD~5?

Предлагает план обработки пяти последних коммитов относительно HEAD~5. pick сохраняет коммит; reword меняет сообщение; edit останавливается для правок; squash объединяет с предыдущим и редактирует сообщение; fixup объединяет, отбрасывая сообщение; drop исключает коммит. Для разделения коммита используют edit и затем несколько новых коммитов.

## 4. Squash и fixup

Оба объединяют изменения с предыдущим коммитом. squash позволяет составить итоговое сообщение из сообщений объединяемых коммитов; fixup обычно оставляет только сообщение предыдущего.

## 5. Для чего cherry-pick?

Создаёт в текущей ветке новый коммит с изменениями выбранного коммита. Например, переносит срочное исправление без соседней экспериментальной функции.

## 6. Как восстановить потерянный коммит?

Найти его SHA в git reflog и создать ссылку: git switch -c recovered <SHA>. Reflog локален и имеет срок хранения; после сборки мусора недостижимый объект может исчезнуть.

## 7. Revert и reset --hard

Revert добавляет обратный коммит и сохраняет опубликованную историю. reset перемещает указатель ветки; --hard также заменяет индекс и рабочие файлы, уничтожая незакоммиченные изменения. Для отмены опубликованного изменения обычно выбирают revert.

## 8. Как настроить два получателя push?

Добавить mirror, затем явно задать origin два pushurl: сначала основной URL, затем URL зеркала. Если сразу добавить только mirror через --add --push, единственным явным pushurl может стать зеркало. Проверять: git remote get-url --push --all origin.

## 9. Что такое Git hooks?

Локальные сценарии, запускаемые в определённых точках Git. pre-commit подходит для проверки файлов до коммита, commit-msg - для проверки сообщения. В бонусном задании проверяется именно commit-msg. Такие hooks не заменяют обязательные серверные проверки CI.

## 10. Forking Workflow

Участник создаёт свой fork, добавляет upstream исходного проекта, работает в своей feature-ветке, синхронизируется с upstream и предлагает изменения через PR. GitHub Flow обычно предполагает ветки одного общего репозитория; fork даёт отдельное пространство прав и remote.
